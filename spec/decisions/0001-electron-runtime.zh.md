# ADR-0001：采用 Electron 作为桌面运行时

[English](0001-electron-runtime.md) | 中文

状态：已接受，待原型验证

日期：2026-08-15

## 背景

目标产品需要像普通 Windows 客户端一样启动、出现在任务栏、自动管理 DSH 后端，并能以安装包或便携包交给没有开发环境的用户。

官方 DSH 要求 Node.js `^22.19.0 || >=24.0.0`，其 Web 前端由 CLI 服务端提供并注入运行时数据。桌面发行版如果依赖用户自行安装正确版本的 Node.js 和 pnpm，就无法达到开箱即用的目标。

## 决策

第一版桌面客户端采用 Electron。Electron 主进程负责桌面生命周期，并将官方 DSH Web 服务作为独立子进程启动；`BrowserWindow` 只加载该服务的回环地址。

我们不在 Electron renderer 中运行 DSH Host，也不重新实现 Agent 核心。主进程和 DSH 子进程保持故障与职责隔离。

## 理由

- Electron 自带兼容的 Node.js 运行时，能减少目标电脑的环境前置条件。
- 当前前端本身是 Web UI，放入 BrowserWindow 的改造量较小。
- 主进程能够可靠管理子进程、窗口、单实例、日志、协议和安装生命周期。
- Windows 安装、便携打包和代码签名已有成熟工具链。
- 与官方 DSH 同属 TypeScript/Node 生态，后续适配和调试成本相对可控。

## 代价

- 安装体积和基础内存占用高于系统 WebView 方案。
- Electron 与内置 Node.js 的安全更新需要纳入发行节奏。
- 打包官方 DSH、插件和动态资源时需要验证运行时闭包。
- BrowserWindow 加载本地 HTTP 服务仍需严格限制导航、IPC 和回环访问。

## 未采用方案

### Tauri

Tauri 的安装体积通常更小，也能使用系统 WebView，但它不能自然消除 DSH 对特定 Node.js 运行时的依赖。若仍需额外打包 Node.js 或把后端改写成 sidecar，第一版的构建、调试和跨机分发复杂度会更高。

### 系统浏览器或 PWA

这种方案实现最轻，但仍保留用户不喜欢的浏览器混杂感，并且后台服务、任务栏身份、退出语义和首次启动体验不够像独立客户端。

### 完整重写原生界面

完整重写会复制官方 Web UI 与协议适配工作，显著增加跟进 Developer Preview 上游变化的成本，也偏离“保留官方 Agent 能力”的原则。

## 验证门槛

进入正式实现前，Electron 技术原型必须证明：打包后无需外部 Node.js；能够启动和优雅停止 DSH；插件和静态资源完整；API Key 配置、会话和附件正常；动态端口与单实例可靠；基础内存和安装体积可以接受。

如果其中存在无法合理解决的阻碍，应新增 ADR 替代本决策，而不是悄悄更换技术栈。
