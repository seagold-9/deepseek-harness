# 桌面客户端架构

[English](desktop-architecture.md) | 中文

状态：计划中

关联决策：[ADR-0001：采用 Electron](decisions/0001-electron-runtime.md)

## 总体方案

桌面客户端使用 Electron 作为薄壳，内置与发行版本匹配的 Node.js 运行时和官方 DSH 代码；Electron 主进程启动 DSH Web 服务子进程，等待本地健康检查通过，再由 `BrowserWindow` 加载回环地址。

官方 Web 前端依赖 CLI 服务端注入运行时启动数据，因此不把静态前端文件直接塞进窗口，也不复制一套独立的 Agent 后端。

```text
Windows dsh.exe
  -> Electron 主进程
     -> 生命周期、单实例、窗口、日志、健康检查
     -> DSH 子进程
        -> 官方 web profile 与 Agent 运行时
        -> 仅监听 127.0.0.1 的动态端口
     -> BrowserWindow
        -> 加载本地 DSH Web UI
```

## 模块边界

### 桌面壳

负责应用启动、单实例锁、窗口状态、任务栏集成、后端进程生命周期、崩溃提示、日志位置、导入导出和发行打包。

桌面壳不实现模型调用、Agent 循环、会话协议或插件协议，这些继续由官方 DSH 拥有。

### DSH 后端

作为独立子进程运行，使用固定的发行内代码和应用指定的 `DSH_HOME`，退出时接收正常终止信号并获得有限的清理时间。

子进程异常退出时，桌面壳展示可理解的错误、日志入口和重试操作；连续重启必须限流，不能形成无限崩溃循环。

### Web 界面

继续使用官方插件化 Web UI，并叠加本项目的桌面主题和独立交互定制。

窗口只允许导航到本次启动的回环来源；外部链接交给系统浏览器打开。

## 运行时与端口

- 使用打包内的 Node.js，不依赖用户预装 Node.js、npm 或 pnpm。
- 后端监听 `127.0.0.1`，禁止默认监听局域网地址。
- 启动时申请可用动态端口，并通过进程间参数传给后端，避免固定端口冲突。
- BrowserWindow 在健康检查前显示本地启动界面，而不是暴露连接失败页面。
- 应用持有子进程句柄和一次性启动令牌，避免误杀用户自行启动的 DSH 实例。

## Electron 安全基线

- `nodeIntegration: false`
- `contextIsolation: true`
- 启用沙箱能力，除非经过记录的兼容性测试证明某个窗口必须例外。
- 不向页面暴露通用文件系统、Shell 或任意进程执行能力。
- preload 只提供最小、带参数校验的 IPC 接口。
- 拒绝未知新窗口、下载和跨来源导航。
- 为本地服务设置随机启动令牌或等效会话校验，降低其他本机页面调用敏感接口的风险。
- 日志默认脱敏，不记录 API Key、Authorization 头或完整凭据文件。

## 用户数据

官方 DSH 数据统一位于 `DSH_HOME`；默认值是 `~/.dsh`。桌面版第一阶段应为自己的发行版选择稳定且明确的 Windows 数据目录，并在启动子进程时显式设置 `DSH_HOME`，最终路径在实现阶段通过迁移测试后冻结。

需要长期保留的内容包括会话、设置、profile、附件和用户插件配置。API Key 目前由官方凭据机制保存在 `$DSH_HOME/.credentials.yaml`，桌面版第一阶段继续复用该机制。

缓存、临时文件和诊断日志应与可迁移数据区分，避免导出包无谓膨胀。

## 导出与迁移

默认导出包含会话、设置、profile 和附件；默认排除 `.credentials.yaml`、`.env`、缓存和日志。

导入前展示包版本和内容摘要，写入前创建可恢复备份，并拒绝路径穿越、符号链接逃逸和未知格式。

另一台电脑上的工作区绝对路径可能不同，因此导入后允许用户逐个重新连接缺失的工作区，不能静默把路径指向错误目录。

如未来提供加密凭据迁移，应作为单独规格设计，不能把明文密钥加入普通导出包。

## 打包与发布

第一阶段生成 Windows x64 NSIS 安装包和便携 ZIP。安装包提供开始菜单、桌面快捷方式、卸载入口和稳定的应用标识；便携包适合试用和手动迁移，但仍将用户数据放在明确位置，除非用户显式启用真正的便携数据模式。

正式向不熟悉开发工具的用户分发前需要代码签名，否则 Windows SmartScreen 会显著增加安装阻碍。发布物应包含 MIT 许可和上游版权声明，并明确标注非官方发行版。

## 版本与兼容

桌面版本绑定一个经过测试的官方 DSH 提交或发行版本，构建过程不得在用户机器上下载“最新版”代码。

建议版本元数据同时保存 `desktopVersion`、`upstreamVersion`、`upstreamCommit` 和 `dataSchemaVersion`。升级前检查数据兼容性；发生不可逆迁移时必须先备份并提供清晰说明。

官方更新的处理方法见[上游更新流程](upstream-update.md)。

## 待验证问题

- DSH Web 服务最稳定的就绪探针和优雅关闭接口。
- 打包后插件解析、原生依赖和动态资源的完整闭包。
- Windows 安装版与便携版使用同一 `DSH_HOME` 还是隔离数据目录。
- 当前官方凭据文件权限在 Windows 上的实际保护程度，以及是否需要接入系统凭据库。
- 官方标志能否用于公开分发的非官方客户端。
