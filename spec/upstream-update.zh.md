# 官方上游更新流程

[English](upstream-update.md) | 中文

状态：计划中

官方 DeepSeek Harness 当前处于 Developer Preview，可能出现破坏兼容性的变更。本项目采用“固定基线、受控合并、完整验证、明确回退”的方式跟进，不在用户设备上自动追踪官方主分支。

## Git 远程约定

当前仓库只有名为 `origin` 的官方远程 `https://github.com/deepseek-ai/deepseek-harness.git`。建立个人 fork 后，目标约定为：

- `upstream`：DeepSeek 官方仓库，只用于 fetch。
- `origin`：个人或项目 fork，用于推送本项目分支和发行标签。

远程调整属于外部仓库操作，等个人 fork 地址确定后执行并记录；当前不凭空创建地址。

## 变更分层

长期历史应尽量保持以下逻辑层次，每层可以由一个或多个小提交组成：

1. `upstream-dsh`：未经改写的官方基线。
2. `desktop-shell`：Electron 生命周期、打包、日志和迁移。
3. `desktop-theme`：紧凑视觉、布局和品牌呈现。
4. `selection-annotation`：选中文字批注等独立交互能力。

这些名称表示维护边界，不要求长期创建四个相互依赖的 Git 分支。默认使用一个可发布主分支和清晰提交历史，避免多分支长期漂移。

## 更新步骤

1. 从当前可发布状态建立保护标签或备份分支，记录桌面版本、上游版本和上游提交。
2. 获取 `upstream` 的目标标签或提交，先阅读官方发行说明、迁移说明和 Developer Preview 破坏性变更。
3. 在独立更新分支合并目标上游，不直接改写已发布历史。
4. 先解决结构和契约冲突，再恢复主题；不要用整文件覆盖的方式强行保留旧 UI。
5. 对每项本地定制判断为“继续保留”“改用官方实现”“重新适配”或“删除”，并更新[现有定制记录](customizations.md)。
6. 执行静态检查、相关单元测试、完整构建、桌面端到端测试和数据升级测试。
7. 在干净 Windows 环境进行安装、首次配置、会话、退出、升级和回退冒烟测试。
8. 更新规格、ADR、第三方声明和发行说明后，才生成正式安装包。

## 冲突处理原则

- 官方已经提供等价或更好的能力时，优先迁移到官方接口，删除重复实现。
- 视觉冲突优先适配官方新 DOM 和 token，不回退官方的数据或交互修复。
- 独立功能必须通过公开 slot、服务或组件契约接入；如果只能修改深层内部实现，应记录维护风险。
- Host 协议、持久化格式、凭据和安全边界的冲突优先级高于外观一致性。
- 无法在一个更新周期内可靠适配时，继续发布旧的已验证基线，而不是带着已知数据风险追新。

## 每次更新记录

每次上游更新应在发行说明或专门的更新记录中写明：

- 旧上游提交与新上游提交。
- 官方版本或标签。
- 采用的官方新能力。
- 本地定制的保留、替换和删除项。
- 手工冲突及解决理由。
- 数据迁移影响。
- 已执行的测试和未覆盖风险。
- 回退目标版本。

## 最低发布检查

```powershell
pnpm run typecheck
pnpm run lint
pnpm run test
pnpm run build
pnpm run verify-md-wrap
pnpm run verify-md-links
git diff --check
```

桌面项目建立后，还必须加入 Electron 单元测试、打包测试、Windows 安装冒烟测试、后端生命周期测试和导入导出测试。具体命令由桌面项目首次实现时写入根脚本，不能长期只存在于个人笔记中。
